# mvmctl 0.3 — full command and environment reference

> mvmctl manages Firecracker microVMs on Linux with KVM. This reference covers the
> 0.3 prerelease. The environment blueprint schema version is `"1"`.

## Using this reference

- Check the installed build with `mvm version`, and use `mvm help <command>` for
  its command-specific usage. For 0.3 VM launch, select the exact matching
  Firecracker/Jailer 1.17.0 pair. The 0.3 installation requires fresh managed state.
- Ordinary operator commands run unprivileged after administrator installation
  and host initialization. Inspect the selected resources before changing them.
  Obtain operator authorization before destructive actions or changes to host
  setup, access policies, and persistent storage.
- For automation, use `--json` on supported finite commands and inspect the
  exit status, response `status`, and per-item errors. A partial result can
  include completed work. Inspect that work before retrying.
- For blueprints, start with `version: "1"` and use named YAML maps for steps.
  Give each reference a direct or transitive `depends_on` path. Review
  `mvm env diff <spec>` against saved workflow state before reapplying, and
  make command and copy steps safe to rerun. Review volume retention before
  destroy. Keep credentials and private keys out of shared specs and prompts.
- Use separate, narrowly scoped grants for service traffic, VM-to-VM execution,
  and floating-IP guest methods. Ask for the exact endpoints and permissions
  before generating grant commands.

## Command Reference

**Root command flags:**

| Flag | Type | Description |
|------|------|-------------|
| `--verbose` | persistent | Enable verbose output |
| `--debug` | persistent | Enable debug mode |
| `--json` | persistent | Emit one schema-versioned response for a supported finite command |
| `--version` | root | Show version and exit |

`--json` applies to reads and mutations. The response has `schema_version: 1`, `status` (`success`, `error`, or
`partial`), command-specific `data`, and `error`. An error preserves its code, class, message, optional operation and
entity, and details. Batch data preserves each result and its structured error. A partial response retains completed
work and exits unsuccessfully; callers must inspect both status and data before retrying. Read results live under `data`. Array-valued resource listings, such as
`key ls`, `vm ls`, and `vm ps`, remain arrays under `data`; an empty result is `[]`, not `null`.

Streaming and interactive commands reject structured output with `cli.output.unsupported`: `exec`, `ssh`, `logs`,
completion, `run`, the `init` wizard, and console attachment. Finite console state and kill commands support it.
Arguments after `--` belong to the guest command and do not select host JSON output.

### General commands

| Command | Description |
|---------|-------------|
| `mvm`, `mvm --help` | Show root help. `--help` and `-h` also work on individual commands. |
| `mvm help [COMMAND...]` | Show help for a command path. An unknown topic exits with an error. |
| `mvm version` | Show the version and build or tag information when available. Supports `--json`. |
| `mvm --version` | Show the version through the root version flag. Supports `--json`. |
| `mvm completion bash`, `mvm completion zsh`, `mvm completion fish` | Write shell completion to standard output. |

The `mvm run` command group is reserved for internal service subprocesses.
Operate console and cloud-init through their documented operator commands and flags.

### Selectors

Resource commands (`inspect`, `rm`, `pull`, etc.) accept **selectors** — flexible
identifiers that the system resolves to a specific resource. Each resource domain
defines its own set of selectors, tried in priority order. The general resolution
pattern is:

1. Try the highest-priority selector.
2. If it matches exactly one resource, return it.
3. If not found, fall through to the next priority.
4. On any other error (DB error, ambiguous match), propagate immediately.

| Domain | Selectors (tried in priority order) |
|--------|-------------------------------------|
| **kernel** | `type:version` → absolute path → ID prefix → type name → relative path |
| **image** | `type:version` → type name → display name → ID prefix |
| **binary** | `type:version` → ID prefix → type name |
| **vm** | Name → IP address → MAC address → ID prefix |
| **network** | Name → ID prefix |
| **volume** | Name → ID prefix |
| **key** | Name → fingerprint prefix → `.pub` file path |
| **snapshot** | Name → ID prefix |

**Notes:**
- **ID prefix** — Every resource is assigned a unique SHA-based ID at creation time.
  Any unique prefix resolves to the resource (minimum length enforced by the DB).
- **VM IP/MAC** — If the input contains `.`, it is treated as an IP lookup. If it
  contains `:`, it is treated as a MAC lookup. Both fail immediately on mismatch
  (no fallthrough to ID prefix).
- **Key fingerprint** — The resolver tries both bare input and `SHA256:`-prefixed
  variants for fingerprint matching.
- **`type:version` shorthand** — The colon-separated format works for kernel, image,
  and binary resources. The type portion alone resolves to the latest version.
- Each resource section below documents its specific selectors with usage examples.

### `mvm init`

First-time operator setup wizard. Coordinates host admission, a default network, cache initialization, and a
Firecracker/Jailer release pair. Kernel, image, and SSH-key setup are separate commands. The approved v0.3.0 launch
contract requires the exact matching Firecracker/Jailer 1.17.0 pair.

```
mvm init [flags]
```

| Flag | Description | Default |
|------|-------------|---------|
| `--non-interactive` | Use defaults, skip all prompts | `false` |
| `--skip-host` | Skip host init step | `false` |
| `--skip-network` | Skip default network creation | `false` |
| `--binary-version <version>` | Download this exact Firecracker version when no local pair exists | empty (interactive choice or latest in non-interactive mode) |

`--binary-version` does not replace an existing default pair. To select the v0.3.0 launch pair when another release is
already installed, run `mvm bin pull firecracker:1.17.0 --default` and check `mvm bin ls` before creating a VM.

### `mvm host`

Host configuration commands for one-time, machine-global setup.

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm host install-system` | — | Administrator-only early bootstrap. Atomically installs the running trusted artifact as root-owned `/usr/local/bin/mvm` without loading user cache, configuration, database, or Cobra state. |
| `mvm host init` | `--operator USER` (direct root only), `--json` | Early administrator setup with a root-owned journal, operator enrollment, and compiled host changes. |
| `mvm host status` | `--json` | Show current host configuration state vs expected |
| `mvm host info` | `--refresh`, `--json` | Show host hardware, limits, and VM capacity projection |
| `mvm host clean` | `-f, --force` | Observe the caller's root VM inventory, then remove its locally registered networks through typed root authority. Refuses running VMs or incomplete observation; does not force-stop VMs or reset shared host settings. |
| `mvm host reset` | `--force`, `--operator USER` (direct root only), `--json` | Early administrator rollback under retained global quiescence. Requires marker-only sudoers and compatible journals; refuses live or ambiguous state rather than force-stopping VMs. Admission remains disabled afterward. |

For full v0.3.0 removal, the separate [administrator uninstall script](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/UNINSTALL.md) cleans all enrolled
operators' managed data, performs host reset, then removes installation files and authority.

`host install-system` accepts only the exact command shown: no flags or extra arguments, including `--json`,
`--debug`, or `--verbose`. It runs before ordinary CLI initialization.

`host info` reads a caller-owned capacity cache, detecting and saving capacity on the first read and again with
`--refresh`. It does not infer administrator setup from that cache. Structured `host info --json` omits `setup`;
`host status --json` reports `data.state: null` rather than claiming root admission from the legacy SQLite bit.

`host status` verifies the fixed managed sudoers policy through authenticated root observation when it cannot
confirm absence directly. Permission denial does not mean the policy is missing. Confirmed absence reports
`data.sudoers_exists: false`; unsafe policy metadata or content, unavailable observation, and a missing or invalid
observer response return an error instead of a successful status result.

The interactive `mvm init` wizard can offer explicit administrator setup even when the operator cannot yet observe
the policy.
It reports that initial state as unverified, then requires successful host-policy and group verification after setup.
If the current session lacks the enrolled group, log out and back in or run `newgrp mvm` before retrying.

On a clean host, run `sudo /usr/local/bin/mvm host init`; sudo selects its invoking non-root account. In a direct-root
session, use `/usr/local/bin/mvm host init --operator USER`. Sudo invocation rejects `--operator`. The early route runs
before user configuration, cache, SQLite, and ordinary service initialization. Its journal beneath
`/var/lib/mvmctl/host` preserves original global state and mutation progress. Separate root-owned
`operator-<uid>.json` records preserve each enrolled operator's prior membership. Multiple operators are supported;
an interrupted initial global transaction must first be recovered by its original operator. The administrator
installs the binary separately with `mvm host install-system`.

Host initialization uses a schema-2 administrator journal and enables privileged admission only after host setup and
operator enrollment complete. v0.3.0 requires a clean installation and fresh managed state.
Missing, disabled, or unsafe admission state blocks ordinary privileged requests.

Generated sudoers permits only the fixed system binary's `__mvm_privileged_v1` marker. Install/init/publication reject
wildcard and raw-tool policies.
Administrator reset is implemented for compatible recorded state: it refuses live or ambiguous ownership, restores
recorded settings through retryable receipts, and leaves admission disabled afterward or after a restoration error.
It does not force-stop VMs, erase authority history, or turn old unowned state into managed state.

The early parser supports JSON boolean forms, help, and argument boundaries. Host clean/reset are not a supported
legacy-state removal procedure in this development build.

### `mvm kernel`

Kernel management — list, pull, remove, inspect, set default, and import kernels.

#### Selectors

The kernel resolver tries selectors in priority order:

1. **`type:version`** — e.g. `official:6.19.9`, `firecracker:v1.15`
2. **Absolute path** — path starting with `/` that exists on disk, e.g. `/home/user/vmlinux`
3. **ID prefix** — unique prefix of the kernel SHA ID
4. **Type name** — matches the kernel type (resolves to latest version), e.g. `official`
5. **Relative path** — path relative to CWD that exists on disk, e.g. `./vmlinux-custom`

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm kernel ls` | `--json`, `-r, --remote`, `--no-cache`, `--long` | List cached kernels (or available remote kernels with `--remote`) |
| `mvm kernel pull` | `[type:version]`, `--type`, `--version`, `--default, -d`, `--jobs`, `--keep-build-dir`, `--clean-build`, `--config`, `--features` | Pull or build a kernel. Supports `type:version` shorthand (e.g. `official:6.19.9`) |
| `mvm kernel import` | `NAME`, `PATH`, `--version`, `--default, -d` | Register a vmlinux file as a kernel in the database |
| `mvm kernel default` | `SELECTOR` | Set a kernel as the default |
| `mvm kernel rm` | `[SELECTORS]...`, `-f, --force` | Remove one or more kernels |
| `mvm kernel inspect` | `SELECTOR`, `--json` | Show detailed information about a kernel |

**`pull` flags:**

| Flag | Description | Default |
|------|-------------|---------|
| `[type:version]` | (positional) type:version shorthand e.g. `official:6.19.9` | — |
| `--type TYPE` | Kernel type: `firecracker` or `official` | — |
| `--version VERSION` | Kernel version | (latest) |
| `--default, -d` | Set as default after fetch | `false` |
| `--jobs N` | Parallel build jobs (official only) | `0` (not explicitly set) |
| `--keep-build-dir` | Keep build directory (official only) | `false` |
| `--clean-build` | Skip cache and force clean build (official only) | `false` |
| `--config PATH` | Custom kernel config file to apply as a fragment | — |
| `--features TEXT` | Comma-separated kernel features (e.g. `kvm`, `nftables`, `tuntap`, `btrfs`). Use `all` or `*` to enable every feature defined in the selected kernel spec. | — |
| `--skip-checksum` | Skip SHA256 checksum verification | `false` |

```
# List available remote kernel versions
mvm kernel ls --remote

# Pull the official kernel at version 6.19.9
mvm kernel pull official:6.19.9

# Pull with custom config fragment
mvm kernel pull --type official --version 6.19.9 --config /path/to/config.fragment
```

### `mvm image`

Image management — download, list, inspect, import, and manage VM images.

#### Selectors

The image resolver tries selectors in priority order:

1. **`type:version`** — e.g. `ubuntu:24.04`, `alpine:3.21`
2. **Type name** — matches the image type (resolves to latest version), e.g. `ubuntu`
3. **Display name** — matches the display name, e.g. `Ubuntu 24.04 LTS`
4. **ID prefix** — unique prefix of the image SHA ID

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm image ls` | `--json`, `-r, --remote`, `--no-cache`, `--type`, `--long` | List cached images (or available remote images with `--remote`) |
| `mvm image pull` | `[SELECTOR]`, `--type`, `--version`, `--force, -f`, `--no-cache`, `--default, -d`, `--skip-optimization`, `--disable-detector` | Download an image by selector |
| `mvm image import` | `NAME`, `VM_SELECTOR` or `PATH`, `--format`, `--root-partition`, `--default, -d`, `--force, -f`, `--skip-optimization`, `--disable-detector` | Import a local image file or create a base image from a VM's rootfs |
| `mvm image default` | `SELECTOR` | Set the default image for VM creation |
| `mvm image rm` | `[SELECTORS]...`, `--force, -f` | Remove cached images by selector |
| `mvm image warm` | `[SELECTOR]`, `--all, -a` | Pre-decompress image to ready pool for fast VM creation (warms all images if omitted) |
| `mvm image inspect` | `SELECTOR`, `--json` | Show detailed information about an image |

**`pull` flags:**

| Flag | Description | Default |
|------|-------------|---------|
| `-t, --type TEXT` | Image type from images.yaml (e.g. `ubuntu`, `debian`, `firecracker`) | (first matching) |
| `--version VERSION` | Version override | (latest) |
| `--force, -f` | Re-download even if cached | `false` |
| `--default, -d` | Set as default after fetch | `false` |
| `--no-cache` | Skip cached version listing and fetch live from upstream | `false` |
| `--skip-optimization` | Skip filesystem optimization | `false` |
| `--disable-detector NAME` | Comma-separated detectors to disable: `type`, `label`, `size`, `filesystem`, `all` | — |

**`import` flags:**

| Flag | Description | Default |
|------|-------------|---------|
| `--format FORMAT` | Image format: `qcow2`, `raw`, `tar-rootfs`, or `auto` | `auto` |
| `--root-partition N` | Root partition number (e.g. 1, 2) | `0` (auto-detect) |
| `--version VERSION` | Set image version | — |
| `--default, -d` | Set as default after import | `false` |
| `--force, -f` | Overwrite existing | `false` |
| `--resume IMAGE_ID` | Resume retained local-image optimization using its full ID; incompatible with `--force` | — |
| `--skip-optimization` | Skip OS cache cleanup (deblob), keep plain ext4 | `true` |
| `--disable-detector NAME` | Comma-separated detectors to disable: `type`, `label`, `size`, `filesystem`, `all` | — |

**Importing from a VM:** `mvm image import NAME VM_SELECTOR` reads the VM's current protected root disk through
the enrolled, typed root dispatcher, not its original operator-visible staging file. A running VM is paused for
the copy and resumed before extraction; already paused or stopped sources retain their state. This produces a
disk image, not a memory or attached-data-volume snapshot. The best-effort guest `sync` hint does not guarantee
application transaction consistency.

Temporary independent copies live under root-controlled `/var/lib/mvmctl/vm-rootfs-export-data/<operator-uid>`
with operator read access. Export copying skips source-reported holes while preserving the logical disk length
and contents. Allow space on that filesystem as well as the selected managed cache, where protected
VM disks and final images remain. Typed cleanup releases the temporary copy after extraction and before final
publication; copy, state-recovery or cleanup failures remain explicit rather than falling back to staging.

An ext4 disk copied while the source VM is paused can still require filesystem journal replay. With LoopMount,
import runs fixed unprivileged `/usr/sbin/e2fsck -p -E journal_only` on a new disposable inspection copy before
the unchanged root read-only OS inspection. This does not modify the protected VM disk, root-controlled export
or extracted source, and it is not general filesystem repair. Journal preparation failure stops the import;
it does not enable a writable inspection mount or discard the journal. See the
[LoopMount dependencies](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/DEPENDENCIES.md#e1-loop-mount-default).

If an interrupted import leaves no public image row, `mvm image rm --force EXACT_64_CHARACTER_IMAGE_ID` can
release its independent export. The read-only `<image-id>.copy` marker in the operator's export directory identifies
the ID; it is not deletion authority. This recovery requires one full lowercase hexadecimal ID and confirmed
repository absence: names, prefixes, multiple selectors and database errors cannot authorize it. A live exporter
reports busy. Copy removal does not clear uncertain source-VM recovery; that condition is reported separately.
Use the typed command, not manual deletion. An open reader can retain unlinked bytes, so successful cleanup does
not promise immediate physical reclamation.

VM-to-image import copies the root disk, not RAM or attached data volumes, and does not promise application-consistent
state across them. Accepted registered journeys and remaining interruption/fault limits are recorded in the
qualification checkpoint. See
[ADR-0018](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/adr/0018-isolated-vm-execution-and-snapshot-authority.md#vm-to-image-import-from-authoritative-backing).

Typed image optimization supports deblob and fstab repair, ext-family offline shrink, and durable Btrfs-to-ext4
conversion as a separate transaction before shrink. XFS supports inspection, provisioning, deblob, and fstab repair
at existing capacity; resize/shrink requests fail before mutation.

Interrupted optimization can resume from exact retained staging intent and resource identities. A checked root result
is required before publication, which requires atomic exchange and preserves the original until durable completion.
Unknown or changed remnants remain for recovery rather than being adopted or recursively removed.
For a local-file import, use `mvm image import NAME ORIGINAL_SOURCE --resume FULL_IMAGE_ID` with the original
optimization options. Failed local imports include `image_id` in their JSON error details. Resume requires an
unregistered ID and intact retained optimization state; it skips extraction and refuses changed resources or intent.
It does not recover VM-source imports or failures after optimization state has already been removed. Preserve the
original source and retained files; do not remove root-owned records manually.
Unprivileged archive construction remains separate; passing registered journeys does not establish every interruption
or replacement-race outcome.

```
# List available remote image types
mvm image ls --remote

# Pull Ubuntu 24.04
mvm image pull ubuntu:24.04

# Import a local qcow2 image
mvm image import my-image /path/to/image.qcow2
mvm image import base-img my-vm
```

### `mvm bin`

Firecracker runtime management — install, list, select, and remove Firecracker/Jailer release pairs. Root authority
fetches or accepts the optional exact mirror archive, verifies it, and atomically publishes the pair in the trusted
release store. Source builds and manually supplied binary paths are unsupported.

The approved VM launch pair is exactly 1.17.0. Binary-management support for an older audited release does not
authorize VM launch with it. Release updates review and qualify the latest stable matching official pair before
changing the pin; the installed runtime does not automatically follow upstream `latest`. See
[runtime guidance](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/RUNTIME.md#vm-launch-and-resource-control).

#### Selectors

The binary resolver tries selectors in priority order:

1. **`type:version`** — e.g. `firecracker:1.15.0`
2. **ID prefix** — unique prefix of the binary SHA ID
3. **Type name** — matches the binary type (resolves to latest semver), e.g. `firecracker`

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm bin ls` | `-r, --remote`, `--limit`, `--json`, `--long` | List local (and optionally remote) Firecracker versions |
| `mvm bin pull` | `TYPE[:VERSION]`, `--default, -d`, `--force, -f` | Install one root-authoritative release |
| `mvm bin default` | `SELECTOR` | Set a binary as the active default |
| `mvm bin rm` | `TYPE:EXACT_VERSION...`, `-f, --force` | Remove exact releases; force hides local advisories only |

```
# List local and remote versions
mvm bin ls --remote

# Select the latest stable release of this type
mvm bin pull firecracker

# Select the newest stable patch in a release series
mvm bin pull firecracker:1.17

# Install and select the required VM launch pair
mvm bin pull firecracker:1.17.0 --default

# Remove the exact architecture-scoped release pair
mvm bin rm firecracker:1.15.0
```

### `mvm vm`

VM lifecycle management — create, start, stop, reboot, pause, resume, remove, list, and inspect VMs.

#### Selectors

The VM resolver tries selectors in priority order:

1. **Name** — exact VM name, e.g. `my-vm`, `test-runner`
2. **IP address** — input contains `.`, e.g. `10.88.0.5` (fails immediately on mismatch, no fallthrough)
3. **MAC address** — input contains `:`, e.g. `06:00:ac:10:88:05` (fails immediately on mismatch, no fallthrough)
4. **ID prefix** — unique prefix of the VM SHA ID

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm vm create` | `NAME [flags]` | Create and start a new Firecracker microVM |
| `mvm vm start` | `[SELECTORS]...` | Start one or more stopped VMs |
| `mvm vm stop` | `[SELECTORS]...`, `-f, --force` | Stop one or more running VMs |
| `mvm vm reboot` | `[SELECTORS]...`, `-f, --force` | Reboot one or more VMs |
| `mvm vm pause` | `[SELECTORS]...` | Pause one or more running VMs |
| `mvm vm resume` | `[SELECTORS]...` | Resume one or more paused VMs |
| `mvm vm rm` | `[SELECTORS]...`, `-f, --force` | Remove one or more VMs |
| `mvm vm ls` | `--json`, `--long` | List all VMs |
| `mvm vm ps` | `--json` | List running VMs (active processes) |
| `mvm vm inspect` | `SELECTOR`, `--json` | Show detailed information about a VM |

If Firecracker resumes but Guest Control reconciliation fails, the VM is recorded as running and the command
reports the Guest Control error. Retry `mvm vm resume` to reconcile the worker.

If creation was interrupted before the VM reached the caller database, `mvm vm rm --force <full-id>` can request
cleanup through the retained root authority. This recovery form accepts exactly one full 32-character lowercase
hexadecimal ID, not a name or ID prefix; existing registered selectors retain their usual behavior and name precedence.
Root authorization and ownership checks still apply: a missing or inadmissible root record is not permission to
delete files. On success, the result reports `caller_artifacts_retained: true`; caller-owned source files, the VM
directory and staging artifacts are preserved. This is not a filesystem orphan sweep.

VM launch and process control use typed root lifecycle transactions and schema-6 instance records separating operator
ownership from per-VM execution credentials. PID values in
output are display projections, never signaling authority. List observes its complete VM selection before filtering
status and propagates observation failures; inspect/get also propagate them. Paused display state requires an observed
live process. Stop preserves endpoint reservations and traffic grants for restart; remove invalidates them through
root before local deletion. Without `--force`, stop requests guest shutdown through an identity-bound Firecracker API
connection and waits on the exact process before authoritative cleanup.

Typed launch now includes console relay composition and raw data volumes with release-derived device limits,
descriptor-only mounts, and no new storage quotas. PCI launch and x86 nested configuration are implemented for the
pinned release; ARM nested launch is rejected and aarch64 runtime qualification remains open. Typed live-volume
operations and snapshot capture/inspect/remove use root authority. Snapshot restore uses the captured topology and
independent protected disks. The qualification checkpoint records the bounded lifecycle and restore evidence.

| Flag | Description | Default |
|------|-------------|---------|

### `mvm snapshot` (alias: `ss`)

Capture/inspect/remove use root-controlled
storage and exclusive protected rootfs/data-volume capture. Restore copies disks into independent protected backing,
retains immutable memory backing, and preserves captured drive IDs and network identity. The public API reserves the
captured IP before root restore; conflicts fail, and an uncertain root outcome keeps the reservation for recovery.
The accepted candidate passed registered snapshot journeys, including networkless and same-network managed restore.
Broader interruption, post-spawn and uncertain-transport recovery remain limited as described in the qualification
checkpoint and ADR-0018.

Create fresh 1.17.0 snapshots and qualify capture and
restore with the same matching release. Captured versions are preserved; no cross-version conversion or compatibility
is promised. See [runtime guidance](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/RUNTIME.md#vm-launch-and-resource-control).

Create, list, inspect, restore, and remove VM snapshots.

#### Selectors

The snapshot resolver tries selectors in priority order:

1. **Name** — exact snapshot name, e.g. `daily-backup`
2. **ID prefix** — unique prefix of the snapshot SHA ID

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm snapshot create` | `VM_SELECTOR`, `--name`, `--pause` | Snapshot a running VM |
| `mvm snapshot ls` | `--json` | List all snapshots |
| `mvm snapshot inspect` | `SELECTOR`, `--json` | Show detailed information about a snapshot |
| `mvm snapshot restore` | `SELECTOR`, `NAME`, `--network`, `--resume`, `--count N` | Restore one or more VMs from a snapshot |
| `mvm snapshot rm` | `SELECTOR`, `--force, -f` | Remove a snapshot |

`snapshot create` writes the full **Snapshot request ID** to stderr before trusted capture, including with `--json`.
Keep that ID until the command completes. If the command is interrupted, `snapshot ls` may omit a root-published
capture; after the root operation settles, use `mvm snapshot inspect <full-id> --json` to check it and
`mvm snapshot rm <full-id> --force` to remove an unwanted artifact. Do not edit the root-controlled files directly.
`snapshot ls` does not discover unindexed root captures, so losing the ID still requires administrator investigation.

### `mvm network floating-ip`

Reserve private IPv4 addresses and administer exact guest permissions. See the
[Guest Control guide](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/GUEST_CONTROL.md) for ownership, fencing, guest commands and service access.

All commands accept `--network, -n NETWORK`; omission selects the default network. Resource selectors accept a
name, full ID, unambiguous ID prefix or IPv4 address in that network. Grant inspection and revocation require the
complete lowercase 32-character grant ID.

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm network floating-ip create NAME` | `--ip IPV4` | Reserve the explicit address, or allocate an available address when omitted |
| `mvm network floating-ip ls` | `--long`, `--json` | List reservations; `list` is an alias |
| `mvm network floating-ip inspect SELECTOR` | `--json` | Inspect fresh root ownership, lifetime, phase and packet authority; guest alias readiness is unobserved |
| `mvm network floating-ip associate SELECTOR VM` | `--generation N`, `--json` | Persist ownership until release, transfer or VM stop; requires an unassociated resource |
| `mvm network floating-ip transfer SELECTOR VM` | `--generation N`, `--json` | Fence the current owner and assign the target VM |
| `mvm network floating-ip release SELECTOR` | `--generation N`, `--json` | Fence and release ownership; alias: `disassociate` |
| `mvm network floating-ip rm SELECTOR` | `--force, -f` | Remove a reservation; force skips confirmation only |
| `mvm network floating-ip delegation grant RESOURCE` | `--vm VM`, `--method METHOD`, `--lease DURATION` | Store one permission for the current VM incarnation |
| `mvm network floating-ip delegation ls RESOURCE` | `--long`, `--json` | List grants, including revoked lifetimes |
| `mvm network floating-ip delegation inspect GRANT_ID` | `--json` | Inspect one exact grant |
| `mvm network floating-ip delegation revoke GRANT_ID` | — | Revoke and fence ownership sustained by that grant |

`--vm` and `--method` are required for grant creation. Methods are `inspect`, `associate`, `renew` and `release`.
Association and renewal require a positive whole-second duration, such as `10s`; inspect and release forbid it.
There is no implicit guest lease. Host assignments are persistent and require no renewal grant. Optional host
`--generation` binds an earlier observation; omission performs a fresh root observation before compare-and-swap.
Association/transfer wait for exact guest alias acknowledgement. Errors after kernel commit do not imply rollback;
inspect before retrying. A persistent lifetime with zero remaining lease is not expired.
Stored permission does not prove session readiness.

### `mvm policy`

Policy management separates TCP/UDP traffic intent from directional VM-to-VM execution grants. The former flat
`mvm policy create/ls/inspect/rm/sync` commands are replaced by the typed families below.

| Command | Flags | Description |
|---------|-------|-------------|
| `mvm policy traffic create` | Exactly one of `--from-network NETWORK` or `--from-vm VM`; exactly one of `--to-vm VM`, `--to-host` or `--to-floating-ip RESOURCE`; optional `--to-network NETWORK` for floating IPs; `--protocol tcp\|udp`, `--port PORT\|START-END` | Apply a root-authorized traffic grant, then project it locally |
| `mvm policy traffic ls` | `--json` | List VM, host-gateway and floating-IP grants with current resource names |
| `mvm policy traffic inspect` | `POLICY_ID`, exactly one of `--from-network` or `--from-vm`, optional `--to-host` or `--to-floating-ip`, `--json` | Inspect intent; add `--to-host` for a host-gateway grant |
| `mvm policy traffic rm` | `POLICY_IDS...`, exactly one of `--from-network` or `--from-vm`, optional `--to-host` or `--to-floating-ip`, `-f, --force` | Revoke the root grant or prove its absence before deleting the local projection |
| `mvm policy traffic labels create` | `--from-vm VM` or repeated `--from-label KEY=VALUE`; `--to-vm VM` or repeated `--to-label KEY=VALUE`; `--protocol`, `--port` | Allow TCP or UDP using current VM labels |
| `mvm policy traffic labels ls` | `--json` | List selector traffic policies |
| `mvm policy traffic labels rm` | `POLICY_IDS...`, `-f, --force` | Remove selector traffic policies |
| `mvm policy exec create` | `SOURCE_VM DESTINATION_VM TARGET_USER` or endpoint flags with `--user USER` | Allow directional execution as one non-root user |
| `mvm policy exec ls` | `--json` | List directional execution policies with current VM names |
| `mvm policy exec rm` | `POLICY_IDS...`, `-f, --force` | Remove one or more execution policies by exact ID or unambiguous prefix |

Exact traffic creation applies the grant through root before updating SQLite; removal requires root revocation or exact
absence first. List and inspect show the local projection. Root success followed by a projection failure is reported
for repair/retry and does not undo the root outcome. Policies may bind exact active or cleaned root endpoints. Stopping
a VM preserves endpoint reservations and grants for restart; removing it invalidates them. A grant to a stopped
endpoint does not create a live network interface.

Labels are exact `key=value` matches. Repeat a label flag to require all values. Use at least one label selector for
`policy traffic labels create`. Exec accepts exact VMs, selectors, or one of each. Only VMs owned by the policy's
operator can match. Traffic grants follow each matched VM’s primary address and its currently admitted floating
addresses. Use an explicit floating-IP destination when access should follow the address across owners.

```bash
mvm policy traffic labels create --from-label role=worker --to-label role=controller --protocol tcp --port 6443
mvm policy exec create --from-label role=worker --to-vm controller-1 --user worker-reader
```

Set initial labels with repeated `mvm vm create --label KEY=VALUE` flags or the VM's `labels` workflow field.
Use `mvm vm labels inspect VM` for the current revision and `mvm vm labels set VM --revision N KEY=VALUE` to replace the label map.
Removing membership blocks existing VM traffic unless another policy still allows it. A remote command already
admitted can finish. Each new command checks the current policy.

Use `--to-host` to reach a host service through the source managed network's gateway. For a network with gateway
`10.25.0.1`, the guest connects to that address, not the workstation's LAN address or `127.0.0.1`:

```bash
mvm policy traffic create --from-vm client --to-host --protocol tcp --port 5432
mvm policy traffic inspect POLICY_ID --from-vm --to-host
mvm policy traffic rm POLICY_ID --from-vm --to-host --force
```

Operators can select any destination port, but every policy must explicitly name its protocol and port/range.
The service must listen on the gateway or a suitable wildcard address; the policy does not expose a localhost-only
listener. `--from-network` grants the selected network's VMs access to its own gateway. Host-to-VM access is not
managed by these policies. JSON lists separate `network_to_vm`, `vm_to_vm`, `network_to_host`, `vm_to_host`,
`network_to_floating_ip` and `vm_to_floating_ip` arrays.

`--to-floating-ip` selects an exact reservation destination. `--to-network` resolves its network (the default
network when omitted); it is invalid for other destinations. The grant follows only that floating address across
owners and grants no delivery while unassociated. It does not grant ownership, the owner's primary address or
other aliases. Inspect and remove select this family with the boolean `--to-floating-ip` alongside the source
family flag. See [service access examples](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/GUEST_CONTROL.md#allow-service-traffic-separately).

Execution grants are directional, independent of IP-network placement, and require an exact non-root target user.
The opt-in API relay now reads and enforces them at runtime. It also requires root-admitted active VM identities;
creating a grant alone cannot make a transitional VM launch eligible. Passing directional execution journeys does
not establish every peer, capacity, deadline, cancellation or private-backend cleanup outcome.

### `mvm exec`

Execute a command inside a VM via the vsock guest agent. If no command is provided, starts an interactive shell session.
Accepts VM selectors (see [mvm vm](#mvm-vm) for resolution order).

```
mvm exec [VM_SELECTOR] [-- <command>...] [flags]
```

| Flag | Description | Default |
|------|-------------|---------|
| `VM_SELECTOR` | VM name, ID, MAC, or IP (positional, required) | — |
| (args after `--`) | Command to execute (omit for interactive shell) | — |
| `--user, -u TEXT` | User to run the command as | `root` |
| `--timeout, -t N` | Vsock agent connect/probe timeout in seconds | `0` uses `defaults.vm.vsock_probe_timeout` (built-in: 5 seconds) |
| `--no-sync` | Skip final `sync()` after command | `false` |
| `--allow-vm-exec` | Permit this non-interactive source command to request policy-authorized VM-to-VM execution | `false` |
| `--port, -p N` | Vsock port for the guest agent | `1024` |

**Examples:**

```
# Interactive shell
mvm exec my-vm

# Run a command
mvm exec my-vm -- ls -la /etc

# With timeout
mvm exec my-vm --timeout 30 -- apt-get update

# As a different user
mvm exec my-vm --user ubuntu
```

An explicit source command can request execution on another VM with:

```bash
mvm policy exec create source-vm destination-vm app
mvm exec source-vm --allow-vm-exec -- mvm-agent remote --user app destination-vm -- command arg
```

The outer source command may run as root or a non-root account; the destination user must be non-root. The relay
requires the exact directional grant and root-admitted active source/destination identities, applies bounded wire and
capacity limits, and writes command-redacted audit records in the user cache. The opt-in outer command and its one
remote request share an absolute five-minute lifetime; `--timeout` still controls connection/probe time. Ordinary
exec, shell, and copy do not enable this source session. The source guest kernel must provide `SO_PEERPIDFD`; the
stock upstream `6.1.155` kernel used by the cached Firecracker CI selection lacks it. Select a capable source kernel
explicitly; see [kernel capability requirements](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/KERNEL.md#reference). This does not change the default kernel.

If an admitted atomic pidfd proves that an opted-in source command exited before publication, the same binding is
still reserved, unclaimed, and unused, and cleanup succeeds without cancellation, the unused source session closes
and ordinary stdout, stderr, and exit status are preserved. Metadata, reservation, cancellation, and cleanup errors
remain fail-closed. This completion publishes no remote-execution authority.
Accepted source-session journeys and remaining fault limits are recorded in the qualification checkpoint.

## Cloud-Init

The effective default is `--cloud-init-mode off` (no cloud-init). When SSH keys are provided without an explicit mode, the system enables direct key injection regardless of mode.

### Modes

| Mode | Flag | Description |
|------|------|-------------|
| **inject** | `--cloud-init-mode inject` | Direct injection into rootfs via the active provisioner backend (loop-mount or GuestFS) |
| **net** | `--cloud-init-mode net` | Serves cloud-init files via HTTP (nocloud-net) |
| **iso** | `--cloud-init-mode iso` | Generates a cloud-init ISO via `cloud-localds`, or uses a provided custom ISO path |
| **off** | `--cloud-init-mode off` | Skips cloud-init entirely (default) |

The typed LoopMount VM path preserves missing-account creation, selected SSH keys, cloud-init injection, and automatic
deblob. A new non-root account uses a free UID/private GID in 1000–60000, a locked password, `/home/<name>`, and `/bin/sh`;
existing accounts are retained. Injected seeds contain fixed `meta-data` and `user-data` leaves plus optional
`network-config`. Requests cannot select arbitrary host paths or guest commands.

Some distro preparation is installed as fixed guest-boot work, including SSH setup, Arch package-key initialization,
and Btrfs balance. Successful host provisioning means those actions were queued, not that the guest has run them.
Typed image conversion/recovery and unprivileged archive construction are separate operations; successful
provisioning does not imply every guest boot action completed.

### How Net Mode Works

The net mode delivers cloud-init configuration via HTTP. Steps below apply to the net mode only.

1. **HTTP Server**: A NoCloud batch binds the managed network gateway on fixed TCP port `8000`; custom ports are rejected.
2. **Firewall Grant**: Root derives the owned gateway service slot from the network identity. Binding must succeed before access is granted.
3. **Kernel Command Line**: The VM boots with `ds=nocloud;seedfrom=http://GATEWAY_IP:8000/`
4. **Configuration Delivery**: cloud-init fetches `meta-data`, `user-data`, and `network-config` via HTTP
5. **Cleanup**: Normal shutdown revokes the grant while retaining the listener socket, then releases the port.

### Net Mode Security Architecture

The security model applies to the net cloud-init mode only:

- One live NoCloud batch occupies each network gateway listener. A bind collision fails; it neither adopts nor kills the existing listener.
- The typed privileged request selects only the owned network, never a custom address, port, protocol, or service.
- The firewall grant represents the fixed gateway TCP `8000` slot; it does not authenticate the current listener process.
- An interrupted process can leave that reserved-slot grant for a subsequent invocation or network teardown; successful ordinary journeys do not establish every interruption outcome.

| `MVM_CONFIG_DIR` | Override config directory | `~/.config/mvmctl` |

Generic image/kernel downloads look up mirror entries by URL filename, not full origin. Configured checksums are
verified, but Firecracker CI kernel downloads have no upstream SHA-256 configured. Different CI releases can publish
different bytes under the same filename (for example, `vmlinux-6.1.155`); those entries are not interchangeable.
Use separate mirror directories for colliding origins and keep the matching artifact in each. A mirror hit without
an expected checksum does not prove origin or CI-release identity. This does not relax the official checksum
verification required for root-owned Firecracker/Jailer installation.

## Cache Directory Structure

```
~/.cache/mvmctl/
├── bin/                  # Legacy non-launch binary workspace
├── kernels/              # vmlinux kernel images
├── images/               # Root filesystem images (.ext4, .btrfs, .img, .raw, .ext4.zst, .btrfs.zst)
├── volumes/              # Persistent disk volume files
├── vms/                  # Per-VM state
│   └── <vm-sha>/         # VM directories named by SHA256 hash
│       ├── rootfs.img
│       ├── cloud-init.iso            # ISO mode only
│       ├── firecracker.json
│       ├── firecracker.log
│       ├── firecracker.console.log
│       ├── firecracker.metrics       # Metrics enabled only
│       └── cloud-init/               # Generated seed inputs
├── workflows/            # Workflow state persistence
├── nocloudnet/           # nocloud-net batch server dirs and logs
├── .mvm-protected/       # Root-controlled store; not caller-editable
│   └── snapshots/<snapshot-id>/
│       ├── capture.json              # Root-authenticated artifact record
│       ├── capture-progress.json     # Interrupted-capture outcome
│       ├── rootfs.img
│       ├── kernel
│       ├── memory                    # Full snapshots only
│       ├── vmstate                   # Full snapshots only
│       └── volume-<drive-id>.raw     # Each captured data volume, when present
├── logs/                 # Application log files
├── mvmdb.db              # SQLite database (canonical asset state)
├── mvmctl.log            # Main application log
├── timing.log            # Performance/timing log
├── audit.log             # Rotating operation log (10MB, 3 backups)
└── ...
```

The VM and snapshot leaf names above are compiled and are not configurable. `MVM_CACHE_DIR` still selects the managed
cache root. Caller-facing console outputs and display-only PID mirrors use
`/run/mvmctl/runtime/<uid>/<vm-id>`; the Firecracker API and vsock sockets use the isolated execution identity's
private `/run/mvmctl/vmm-runtime/<uid>/<vm-id>` directory, mounted at `/vmm-runtime` inside the jail. The API is
available through the authenticated root broker, not a public `api_socket_path` field. The root transaction pins
individual persistent resources; it does not mount the whole caller-owned VM directory.

The v0.3 privileged path accepts a managed cache root on ext2/ext3/ext4, XFS, Btrfs, F2FS, bcachefs, tmpfs, or ZFS.
FUSE, remote, overlay/stacked, and automount cache roots are unsupported. The descriptor-pinned cache foundation is
implemented. Its private base-resource preparation also replaces admitted caller configuration bytes with a root-built
sealed memfd consumed by typed privileged launch and descriptor-only mounting. These paths have not been qualified.

Canonical launch assets and jail state are outside the user cache:

```text
/var/lib/mvmctl/
├── binaries/<architecture>/<version>/  # Root-owned exact Firecracker/Jailer release pair
└── jailer/firecracker/<vm-id>/root/  # Per-VM jail and bind mounts
```

## Overview

An env spec is a YAML file that describes an environment — networks, SSH keys, images, kernels, binaries, VMs, and the commands that configure them. Running `mvm env apply spec.yaml` provisions everything in dependency order. Section examples below are fragments to combine under one `version: "1"` header; the [full example](#full-example) includes its prerequisites.

The format uses **typed top-level sections** (one per step type) with **map keys as step names**:

```yaml
version: "1"
ephemeral: false

network:
  my-net:
    subnet: "172.27.0.0/24"
```

The map key (`my-net`) is the step name used in references, `depends_on`, `removes`, and saved state. A resource `name` override does not change that step name.

Cross-step references use the **`@type:name`** format:

```yaml
vm:
  dev-vm:
    network: "@network:my-net"
    depends_on:
      - "@network:my-net"
```

The `@` sigil makes references visually distinct from literal values.

---

## Compatibility

Only spec version `"1"` is supported. The available sections are `network`, `floating_ip`, `floating_ip_grant`, `key`, `image`, `image_import`, `kernel`, `binary`, `vm`, `volume`, `traffic_policy`, `exec_policy`, `ready`, `exec`, `ssh`, and `copy`. Snapshot creation and restore are separate CLI operations.

VM steps use the current VM creation rules, including networkless placement, raw data volumes, and the Firecracker `1.17.0` launch requirement. `exec.allow_vm_exec` opts a command into VM-to-VM execution; a directional exec policy is also required. Neither a traffic grant nor an exec grant enables that option implicitly.

Validation rejects unknown sections and fields, malformed or missing references, missing dependency paths, self-dependencies, cycles, unsupported values, and VM `count` values other than `1` before applying steps. Nested `env` and `cpu_config` maps retain their own keys.

Reapply ensures recorded resource identities. It does not silently replace missing resources or mutate changed owned declarations: resolve the reported conflict or explicitly destroy and recreate the affected environment, preserving needed data first. Exec, SSH, copy, and readiness steps run again. Write commands and readiness checks so repeated execution is safe. `mvm env diff spec.yaml` compares the spec with saved state; it does not inspect live configuration drift.

`mvm env apply` and `mvm env destroy` look for `mvmctl.yaml`, then `mvmctl.yml`, when no argument is given. Apply also accepts an HTTP or HTTPS spec URL. `mvm env diff` requires a spec path or workflow ID. The aliases `up` and `down` mean `apply` and `destroy`.

## Top-Level Fields

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `version` | `string` | — | **Required.** Currently only `"1"`. |
| `ephemeral` | `bool` | `false` | Attempt teardown after pipeline success or failure. Shared assets and pre-existing resources are preserved; cleanup errors can leave resources or state behind. |

## Syntax

```yaml
version: "1"

network:
  <name>:               # ← map key = step name
    subnet: ...          # ← step-specific fields

key:
  <name>:
    algorithm: ...
```

Each section is a map from step name to parameters, not a YAML list. The syntax block above is a template; the [full example](#full-example) is a complete spec.

### Common fields

Every step supports dependency and removal lists:

| Field | Type | Description |
|-------|------|-------------|
| `depends_on` | `[]string` | List of `"@type:name"` dependencies. |
| `removes` | `[]string` | Resources to remove after the entire pipeline succeeds. |

`network`, `floating_ip`, `key`, `vm`, `volume`, and `image_import` accept a `name` override, defaulting to the step name. `image.name` is an optional image name; omission uses image acquisition naming. Other steps do not use `name` as a resource-name override.

`network`, `floating_ip`, `key`, and `vm` also accept `existing: <name-or-id>` to select a pre-existing resource without taking
ownership. Do not combine `existing` with creation fields; `floating_ip` still requires `network`. On reapply the saved identity is required; there is no
fallback to a replacement with the same name. The creation-field requirements below apply when `existing` is absent.

---

## References

Cross-resource references use the `@type:name` format:

```yaml
depends_on:
  - "@network:default"
  - "@key:main-key"
  - "@image:os-image"

vm:
  dev-vm:
    network: "@network:default"
    key: "@key:main-key"
    image: "@image:os-image"
```

The `@` prefix distinguishes references from literal string values. The type prefix (`network`, `key`, `image`, etc.) disambiguates steps with the same name under different types.

References do not create dependencies automatically. Each referenced step must be reachable through `depends_on`, directly or transitively; independent steps can run concurrently. References resolve recorded resource identities, including when the resource has a different `name`. Use `@key:name` in `ssh_keys` and `@volume:name` in `volumes`, or literal names/IDs for existing resources. Copy endpoints can use `@vm:name:/path` or a literal `vm-name:/path`. Commands, local paths, environment values, and other literal strings keep their `@` characters.
There is no generic output interpolation: `@floating_ip:api` resolves only in typed resource fields, not inside
`cmd` or `env` strings. To pass a resource ID to a guest helper, inspect it on the host and supply the validated ID
as an ordinary explicit command argument.

## Step Types

### `network`

Create a network for VMs to connect to.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `subnet` | `string` | **Yes** | — | Canonical masked IPv4 CIDR wholly inside RFC1918 space, prefix length at most `/30`; e.g. `"172.27.0.0/24"`. |
| `nat_enabled` | `bool` | No | `true` | Enable IPv4 NAT. |
| `nat_uplink` | `string` | No | `auto` | Discover the default-route interface, use `none` to disable NAT, or name an existing host interface. |
| `nat_uplink_gateway` | `string` | No | — | On-link IPv4 next hop for a named uplink. |
| `ipv4_gateway` | `string` | No | First usable address | Canonical usable IPv4 address inside the subnet. |
| `default` | `bool` | No | `false` | Set as default network. |

For a named uplink, mvmctl manages guest egress routing. See [Network commands](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/REFERENCES.md#mvm-network).

**Example:**
```yaml
network:
  default:
    subnet: "172.27.0.0/24"
    nat_enabled: true
    default: true
```

### `floating_ip`

Reserve an IPv4 address without associating it. An explicit network is required; environment steps do not use
the CLI's default network. See [Guest Control and floating IPs](https://github.com/AlanD20/mvmctl/blob/5426a788ce02d87a5c6e4dbb90d7854d2e38d8d1/docs/GUEST_CONTROL.md) for delegation and fencing.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `network` | `string` | Yes | — | Network selector or `@network:name`. |
| `name` | `string` | No | Step name | 1–63 characters, starting with a lowercase letter or digit; then lowercase letters, digits, `_` or `-`. Reserved names and IP literals are rejected; e.g. `api`. |
| `ipv4` | `string` | No | Allocate | Canonical usable IPv4 in the selected subnet, e.g. `10.25.0.100`; excludes the gateway, primary and floating reservations. |
| `existing` | `string` | No | — | Select and preserve an existing reservation by name, ID, prefix or IPv4. Keep `network`; omit `name` and `ipv4`. |

This complete spec allocates an address before any VM uses the network:

```yaml
version: "1"
network:
  cluster:
    subnet: 10.25.0.0/24
floating_ip:
  api:
    network: "@network:cluster"
    depends_on: ["@network:cluster"]
```

The workflow saves its chosen immutable resource ID before creation. Retries use that ID, including after an
unknown outcome. Reapply refuses a replacement with the same name or address. Destroy removes only its saved
owned reservation and preserves `existing` selections; active ownership must be fenced before retirement.

### `floating_ip_grant`

Delegate guest methods on one floating IP to an explicit list of VMs in its network. Each VM and method
pair gets its own grant for the admitted VM launch.

| Field | Type | Description |
|-------|------|-------------|
| `network` | `string` | Required network selector or `@network:name`. |
| `resource` | `string` | Required floating-IP selector or `@floating_ip:name`. |
| `vms` | `list` | One or more distinct VM selectors or `@vm:name` references. |
| `methods` | `list` | One or more entries with a distinct `method` and a `lease` where required. |
| `methods[].method` | `string` | One of `inspect`, `associate`, `renew`, `release`. |
| `methods[].lease` | `string` | Required for associate and renew. Use a positive whole-second duration such as `10s`. Omit for inspect and release. |

```yaml
floating_ip_grant:
  api-controllers:
    network: "@network:cluster"
    resource: "@floating_ip:api"
    vms:
      - "@vm:controller-1"
      - "@vm:controller-2"
    methods:
      - method: inspect
      - method: associate
        lease: 10s
    depends_on:
      - "@floating_ip:api"
      - "@vm:controller-1"
      - "@vm:controller-2"
```

The workflow saves every grant ID before creation. Each VM's first receipt pins the launch for that VM's other
methods. After an interrupted apply, retry uses the saved IDs. Destroy recovers missing receipts from root using
those IDs and keeps the saved plan until cleanup succeeds. Delegation gives the guest permission to call a method.
The guest must still call it to acquire or renew an address.

If you applied an environment with the earlier development build's `vm`, `method`, and `lease` fields, destroy
it with that build before switching to the batch format.

| `no_network` | `bool` | No | `false` | Create without a network interface. Conflicts with `network`, `guest_ip`, `guest_mac`, network boot arguments, and NET cloud-init. |
| `skip_ci_network_config` | `bool` | No | `false` | Skip generated cloud-init network configuration. |
| `custom_cloud_init_config` | `string` | No | Absent | Path to custom cloud-init user data. |
| `cloud_init_mode` | `string` | No | `off` | One of `off`, `inject`, `net`, `iso`. |
| `cloud_init_iso_path` | `string` | No | Absent | Existing cloud-init ISO path; also set `cloud_init_mode: iso`. |
| `keep_cloud_init_iso` | `bool` | No | `false` | Keep a generated cloud-init ISO. |
| `volumes` | `[]string` | No | `[]` | `@volume:name` references or existing raw data-volume names/IDs to attach. |
| `count` | `int` | No | `1` | Only `1` is accepted. Declare a separate named step for each VM. |
| `atomic` | `bool` | No | `false` | Batch rollback option; use separate VM steps instead of batches in specs. |
| `skip_cleanup` | `bool` | No | `false` | Skip cleanup on failure. |
| `skip_deblob` | `bool` | No | `false` | Skip image deblobbing. |
| `vsock_port` | `int` | No | Config default | Vsock port. Default: `1024`. |
| `writeback` | `bool` | No | Config default | Writeback cache mode. |

Omit `nocloud_net_port`: any explicit value is rejected. NET cloud-init uses reserved gateway TCP port `8000`. QCOW2 remains supported for image import; the raw-only restriction applies to attached data volumes.

**Example:**
```yaml
vm:
  dev-vm:
    labels:
      cluster: demo
      role: worker
    network: "@network:default"
    key: "@key:main-key"
    image: "@image:os-image"
    kernel: "@kernel:fc-kernel"
    binary: "@binary:fc-bin"
    vcpu: 2
    mem: 2048
    disk_size: "10G"
    depends_on:
      - "@network:default"
      - "@key:main-key"
      - "@image:os-image"
      - "@kernel:fc-kernel"
      - "@binary:fc-bin"
```

### `volume`

Create a raw data volume or select an existing volume without taking ownership. Volumes are retained by default, including during ephemeral cleanup, and retained owned volumes keep their state entry. Use `retain: false` at creation for disposable workflow data. Existing volumes are never deleted by the workflow; combining `existing` with `retain: false` is rejected.

To retire retained data after teardown, preserve anything needed, remove the exact saved volume with
`mvm volume rm <volume-id>`, then rerun `mvm env destroy <workflow-id>` to clear its absent state entry.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `name` | `string` | Step name | Name for a new volume. |
| `size` | `string` | — | Required when creating, e.g. `"10G"`. |
| `read_only` | `bool` | API default | Create a read-only volume. |
| `shareable` | `bool` | API default | Permit sharing subject to normal volume rules. |
| `writeback` | `bool` | API default | Writeback cache mode. |
| `existing` | `string` | Absent | Select an existing volume by name or ID. Do not combine with creation options. |
| `retain` | `bool` | `true` | Preserve workflow-created data on destroy; `false` explicitly permits its deletion. |

```yaml
volume:
  data:
    size: "10G"
    retain: true
vm:
  database:
    volumes: ["@volume:data"]
    depends_on: ["@volume:data"]
```

This fragment uses configured VM defaults. It creates an unformatted raw disk; format and mount it through guest provisioning as needed. There is no QCOW2 data-volume mode.

### `traffic_policy`

Allow TCP or UDP traffic to a destination VM, floating IP or the source network's host gateway. Same-network VM traffic also requires grants. A policy does not grant command execution.

| Field | Type | Description |
|-------|------|-------------|
| `source_network` | `string` | Source network selector or `@network:name`; mutually exclusive with `source_vm`. |
| `source_vm` | `string` | Source VM selector or `@vm:name`; mutually exclusive with `source_network`. |
| `source_labels` | `map` | Require all listed labels on the source VM. |
| `destination_labels` | `map` | Require all listed labels on the destination VM. |
| `destination_vm` | `string` | Destination VM selector or `@vm:name`; mutually exclusive with the other destination fields. |
| `destination_host` | `bool` | Set `true` for the source managed network's host gateway, not the host's LAN address or localhost. |
| `destination_floating_ip` | `string` | Floating-IP selector or `@floating_ip:name`; mutually exclusive with VM/host destinations. Requires `destination_network`. |
| `destination_network` | `string` | Explicit network selector or `@network:name`; required only with `destination_floating_ip`, forbidden otherwise. |
| `protocol` | `string` | `tcp` or `udp`. |
| `port` | `string` or `int` | Destination port or inclusive range, e.g. `5432` or `"8000-8080"`; bounds 1–65535. |
| `existing` | `string` | Select an existing policy by exact ID, verified against the declared source, destination, protocol, and port/range. |

Both creation and existing selection require exactly one source, one destination, protocol, and port/range.
Label selectors pair with another label selector or an exact VM. With `existing`, these fields must match the selected grant. Existing selection preserves the policy on destroy.

Operators may select any host port, but must explicitly declare its protocol and port/range. The host service must
listen on the gateway or a suitable wildcard address. Host-to-VM access remains outside policy management.

```yaml
traffic_policy:
  database-access:
    source_vm: "@vm:app"
    destination_vm: "@vm:database"
    protocol: tcp
    port: 5432
    depends_on: ["@vm:app", "@vm:database"]
  host-database-access:
    source_vm: "@vm:app"
    destination_host: true
    protocol: tcp
    port: 5432
    depends_on: ["@vm:app"]
```

A floating-IP destination binds the immutable reservation and its exact address. Access follows the active owner;
it does not expose that VM's primary address or other aliases. No delivery is granted while unassociated. Ownership
requires separate delegation; a traffic policy does not create it.

This complete spec selects an existing network and reservation and permits only TCP 6443 from that network:

```yaml
version: "1"
network:
  cluster:
    existing: cluster
floating_ip:
  api:
    network: "@network:cluster"
    existing: api
    depends_on: ["@network:cluster"]
traffic_policy:
  api-access:
    source_network: "@network:cluster"
    destination_floating_ip: "@floating_ip:api"
    destination_network: "@network:cluster"
    protocol: tcp
    port: 6443
    depends_on: ["@floating_ip:api"]
```

Floating-IP policy steps save exact resolved endpoint IDs and an ownership claim before applying the grant. Retries
and destroy use those saved IDs, so a renamed or recreated endpoint is not adopted. Existing policy selections
must match the declared floating resource and network and are preserved on destroy.

### `exec_policy`

Create a directional VM-to-VM execution grant for one non-root destination user. This does not create that user, enable `exec.allow_vm_exec`, or grant host access. With `existing`, supply the matching source, destination, and target user to verify and preserve the selected policy.

| Field | Type | Description |
|-------|------|-------------|
| `source_vm` | `string` | Source VM selector or `@vm:name`. |
| `source_labels` | `map` | Require all listed labels on the source VM. |
| `destination_labels` | `map` | Require all listed labels on the destination VM. |
| `destination_vm` | `string` | Destination VM selector or `@vm:name`. |
| `target_user` | `string` | Required non-root guest user for creation or existing selection. |
| `existing` | `string` | Select an existing policy by exact ID, verified against the declared endpoints and target user. |

```yaml
exec_policy:
  app-maintenance:
    source_labels:
      role: app
    destination_vm: "@vm:database"
    target_user: app
    depends_on: ["@vm:database"]
```

### `ready`

Wait for a guest command to exit successfully through the vsock agent. Checks rerun on every apply. The deadline includes connection attempts, command execution, and retry waits; cancellation stops the check. Invalid input and authority failures are terminal errors.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `target` | `string` | — | Required VM selector or `@vm:name`. |
| `cmd` | `string` | — | Required guest check command; zero exit status means ready. |
| `user` | `string` | Config default | Guest user for the check. |
| `timeout` | `int` | `60` | Positive total deadline in seconds. |
| `interval` | `int` | `1` | Positive retry interval in seconds. |

```yaml
ready:
  database-up:
    target: "@vm:database"
    cmd: "test -f /run/database-ready"
    timeout: 60
    interval: 1
    depends_on: ["@vm:database"]
exec:
  configure-app:
    target: "@vm:app"
    cmd: "echo database-ready"
    depends_on: ["@vm:app", "@ready:database-up", "@traffic_policy:database-access"]
```

The marker is an example: use a command that checks your application's actual readiness. Consumers must depend on the ready step. This is a guest check, not a host shell or host-port probe. Its total deadline is specific to readiness; ordinary `exec.timeout` and CLI `--timeout` keep their connection/probe meaning.

### `exec`

Run a command inside a VM via vsock agent.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `target` | `string` | **Yes** | — | VM name, ID, IP, or MAC. |
| `cmd` | `string` | **Yes** | — | Command to execute. |
| `user` | `string` | No | Config default | User to run as. |
| `timeout` | `int` | No | `0` (configured probe timeout) | Positive values override connection/probe timeout in seconds. Command execution has no absolute timeout; cancellation stops it. |
| `port` | `int` | No | `0` (auto) | Vsock port override. |
| `env` | `map[string]string` | No | `{}` | Environment variables. |
| `ignore_errors` | `bool` | No | `false` | Continue on non-zero exit. |
| `no_sync` | `bool` | No | `false` | Skip guest filesystem sync after the command. |
| `allow_vm_exec` | `bool` | No | `false` | Allow this command to request VM-to-VM execution under an existing directional exec policy. |

`mvm env apply --env KEY=VALUE` overrides the same key in exec-step `env` maps. It does not alter SSH steps or interpolate YAML fields.

**Example:**
```yaml
exec:
  setup-app:
    target: dev-vm
    cmd: "uname -a"
    user: root
    timeout: 30
    depends_on:
      - "@vm:dev-vm"
```

## Destroy Behavior

`mvm env destroy` tears down resources created by the workflow in reverse dependency order. Resources that existed before apply are preserved. Exec, SSH, and copy side effects are not undone.

| Step Type | Destroy Behavior |
|-----------|-----------------|
| `network` | Deleted — bridge, NAT rules, DB record |
| `key` | Deleted — key files, DB record |
| `vm` | Deleted — runtime stopped, TAP removed, data volumes detached, VM record removed |
| `volume` | Retained by default; delete only workflow-created volumes declared `retain: false`, after dependent VMs |
| `traffic_policy` | Revoke the exact workflow-created grant before its endpoints; preserve existing policies |
| `exec_policy` | Revoke the exact workflow-created grant before its endpoints; preserve existing policies |
| `ready` | No-op — checks have no teardown action |
| `image` | Preserved — cached asset, not destroyed |
| `image_import` | Preserved — cached asset, not destroyed |
| `kernel` | Preserved — cached asset, not destroyed |
| `binary` | Preserved — cached asset, not destroyed |
| `ssh` | No-op — ephemeral side-effect |
| `exec` | No-op — ephemeral side-effect |
| `copy` | No-op — ephemeral side-effect |

### Explicit removals (`removes`)

The `removes` field requests removal after the whole pipeline succeeds. It does not free resources between steps.
Kernels are always retained by environments: a kernel reference in `removes` is rejected before effects. Manage
kernel retirement separately through the kernel CLI. For example, this fragment captures a builder image before
requesting removal of the builder VM:

```yaml
image_import:
  capture-base:
    source: "@vm:builder"
    depends_on: ["@vm:builder"]
    removes:
      - "@vm:builder"
```

### Ephemeral specs (`ephemeral: true`)

Set `ephemeral: true` beside `version` to attempt teardown after pipeline success or failure. Cached images, kernels, binaries, retained volumes, and pre-existing resources remain available. Cleanup failures are returned alongside any original apply failure and can leave resources or state behind; inspect `mvm env ls` and retry `mvm env destroy` when necessary.

## State File

After `mvm env apply`, state is persisted to `~/.cache/mvmctl/workflows/<wf-id>/state.yaml`:

```yaml
workflow_id: "ec729934a8fb9c67"
spec_path: "./my-env.yaml"
schema_version: "1.0"
created_at: "2026-07-05T10:00:00Z"
updated_at: "2026-07-05T10:05:00Z"
resources:
  - name: "network:default"
    type: "network"
    depends_on: []
    state:
      spec:
        subnet: "172.27.0.0/24"
      output:
        network_id: "net-abc123"
      meta:
        was_created: true
        spec_hash: "a1b2c3..."
```

| Field | Description |
|-------|-------------|
| `name` | Internal name (`type:name` format, no `@` sigil) |
| `type` | Resource type |
| `depends_on` | Explicit dependencies |
| `state.spec` | Input spec fields from the YAML |
| `state.output` | Created resource state (IDs, properties) |
| `state.meta.was_created` | `true` if created by workflow |
| `state.meta.spec_hash` | Hash of input spec YAML for drift detection |

Resource identities and ownership are persisted after acquisition. Saved `was_created` stays bound to that identity; finding a different object with the same name never transfers ownership. Policy cleanup checks the exact policy incarnation and durable workflow claim atomically; that claim only restricts cleanup and grants no new policy authority. Persistence and cleanup failures are reported, with remaining state retained for retry. Reapply reruns commands, copies, and readiness; it is not a transactional resume or live configuration reconciliation.
